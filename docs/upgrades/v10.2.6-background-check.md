# Selected v10 background migration check — 2026-11-03

Five real v10 workers passed on the disposable PostgreSQL 15 fixture after the
31 schema migrations. They performed their own operations and wrote their own
completion records; the test did not stamp completion to bypass prerequisites.
No live database, node or deployment was accessed.

| Worker | Result on the synthetic fixture |
| --- | --- |
| `EmptyInternalTransactionsData` | Normalized call types, zero values, trace addresses, errors and created-contract destination fields |
| `ReindexDuplicatedInternalTransactions` | Deleted both traces from a deliberately duplicated block and queued its consensus block for reindexing |
| `CreateInternalTransactionsBlockNumberTransactionIndexIndexUniqueIndex` | Waited for both prerequisites, then built the unique index |
| `ValidateInternalTransactionsBlockNumberTransactionIndexNotNull` | Validated both constraints and set the columns non-null |
| `UpdateInternalTransactionsPrimaryKey` | Replaced `(block_hash, block_index)` with `(block_number, transaction_index, index)` |

All five reached `completed` through their worker code. Restarting them from
those persisted states left the remaining trace rows unchanged and repopulated
the completion cache. Catalog checks verified the new primary-key columns,
index validity/readiness and validated constraints. A duplicate key was rejected;
legacy key columns could become null inside a transaction that was rolled back.

The fixture used the previously recorded v9/v10 image IDs, Linux ARM64 and
PostgreSQL 15.19. It contained three valid traces and two deliberately duplicated
traces attached to consensus/non-consensus blocks at the same height. The local
test changes worker poll intervals and batch sizes only for these disposable
instances. It starts the declared Mix/ConCache dependencies and cache needed by
the standalone workers; it does not start the full Blockscout application.

## Historical-state implication

The fixture deliberately placed the duplicate block outside
`TRACE_BLOCK_RANGES=176114083..latest` and left the internal-transaction fetcher
stopped, matching the relevant dev policy. The duplicate repair removed its two
traces and inserted a pending operation for block 20. The five migration records
then reached `completed` while that block remained pending and untraceable under
the configured range.

This demonstrates a distinction that matters for dev: **completion of the
primary-key prerequisites does not establish recovery of deleted traces**. The
real Nitro database lacks some earlier state, and dev's trace fetcher is disabled.
If the real duplicate-repair worker finds old duplicates, its reindex requests
may be impossible to satisfy using the current node. The fixture does not prove
that the live database contains duplicates or that any live rows have been lost.

The normalization worker also intentionally clears or relocates legacy fields;
these are data changes, not just an index build. Review existing records, backup
recovery, application compatibility and the reindex strategy before enabling
these workers on the real database. Do not mark the migrations complete manually.

```bash
cd /data/blockscout-v10-rehearsal

```

Update this separate checkout to the pushed preparation branch first. The command
uses the existing dev backend Repo in a read-only transaction with 1.5-second

not query trace rows, group duplicates, fetch chain RPC data, start a worker,
create an index or change a service. `estimated_rows=-1` means no usable estimate,
and the index list reports whether it was limited.

Its `duplicate_presence` stays `not_measured`. The index metadata helps select a
subsequent bounded data audit; catalog reads alone cannot establish that the
database is duplicate-free. A full data audit, restored-database rehearsal and
recovery plan remain outstanding.
