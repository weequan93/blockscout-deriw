# Hold the expensive periodic indexer metrics during normalization

The live preparation stopped on a 323-second client transaction. Subsequent
read-only diagnostics identified PID `32950`, active for 1,260 seconds with a
snapshot, no assigned write XID, a `DataFileRead` wait and AccessShare locks on
`blocks` only. The SQL fingerprint
`d63aea58d81cc7d2d9c7ad5cd82809dd` exactly matches
`Explorer.Chain.Metrics.Queries.IndexerMetrics.missing_blocks_count/0` for one
open-ended range. This identifies the hourly monitoring query, independently of
SQL parameters or row values.

The query generates the configured block-number range, counts missing consensus
blocks and sums the results, using `timeout: :infinity`. The caller is
`Indexer.Prometheus.Metrics`, supervised by `BlockScoutWeb.Supervisor`. It schedules
itself hourly and launches several health-metric queries. Cancelling just its
current task can restart the worker and start another scan. A reversible hold of
that worker avoids the repeated scan while retaining the normalization guards.

## Apply the scoped runtime hold

Use the committed tooling revision supplied with the command. On the dev server:

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_metrics_hold.py --hold \
  --upgrade-state /data/blockscout-dev-private/v10-upgrades/upgrade-20261104T032739Z-96b06eb3/state.json \
  --pid 32950 --query-start '2026-11-04 08:30:20.496611+00'
```

The command checks the active image, runtime and readiness, observes the expected
supervised child and query, then freezes a private journal and client before any
runtime change. It prints the effect and state path before requesting the hold.
`--prepare` performs the observation/journaling only; `--resume --state HOLD_STATE`
applies or reconciles that preparation. The source revision is pinned for changes.

Holding terminates only the `Indexer.Prometheus.Metrics` supervised child, leaving
its child specification available for restoration. Other web supervisor children
must retain their identities. The worker's linked database tasks normally exit
with their owner. If the original monitoring query remains active, cancellation
rechecks PID, backend start, query start, fixed SQL fingerprint, database, role
and absence of an assigned write XID before calling `pg_cancel_backend`.
No backend session is terminated. A changed live target causes preparation to
stop without changing runtime; an already-exited target needs no cancellation.

The API, live indexer and NFT worker retain their supervisors and containers.
Periodic indexer health-metric refreshes are paused, so those gauge values may
remain stale. Other instrumentation/exporters are not the target of the hold.
No database rows, migration records, persistent environment or application image
are changed. Active deployment readiness is checked again after the operation.

## Status, recovery and restoration

Copy the private `state` path printed under
`/data/blockscout-dev-private/v10-metrics-holds/hold-.../state.json`.

```bash
python3 deploy/scripts/v10_metrics_hold.py --status --state HOLD_STATE
python3 deploy/scripts/v10_metrics_hold.py --resume --state HOLD_STATE
```

Status is observation only. A lost response leaves `hold_requested` durable;
resume observes an already-stopped child and does not restart it. Original query
identity is checked again before any cancellation, including reconciliation.
If the original query remains active after the bounded cancellation observation,
the journal remains requested for review; do not infer success from a sent signal.

The hold is local to this running supervision tree. A backend/application
supervisor restart can start metric collection again. Check status before the
next normalization epoch. A different Docker deployment is refused by this
journal rather than modified. Do not re-use this hold journal on another server.

After maintenance, explicitly restore on the creation revision:

```bash
python3 deploy/scripts/v10_metrics_hold.py --restore --state HOLD_STATE
```

Restoration starts only the saved metrics child and is idempotent if it is
already running. It immediately starts collection again, including the expensive
missing-block query. A restored journal cannot be applied as a new hold.
For a long-term deployment, separately review a bounded/optional missing-block
metric or an explicit metrics policy; this runtime hold does not implement that
application change.

Once the hold is verified, prepare a **new** normalization session from the
latest applied batch. Failed/incomplete session journals remain retained. Their
old write windows and filesystem baselines are not reset. The next preparation
must still pass current transaction, space, dead-row and WAL checks; the hold
does not relax any normalization budget or enable global migrations.

## Validation

Unit cases cover observation-only preparation, requested-state durability,
lost-response reconciliation, idempotent hold/restore, wrong query identities,
changed deployments and frozen-input integrity. A disposable PG15 fixture runs
the actual compiled metrics worker under a one-for-one supervisor with an
unrelated sibling. A synthetic table lock holds its real missing-block query;
the fixture rejects an incorrect query start, holds/releases the original query,
repeats the hold, restores and holds again. The sibling and migration records
must remain unchanged. No live service is accessed by that fixture.
