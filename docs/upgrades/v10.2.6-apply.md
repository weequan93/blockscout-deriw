## Prepare without downtime

Use the updated tools in the existing clean upgrade checkout. They allow the
verified candidate's application/config/recipe source to remain pinned while
later commits update only deployment tools or upgrade documentation. No image
rebuild is needed for this runner.

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_upgrade.py --check \
  --private-file /data/blockscout-dev-private/private-20261103.json \
  --receipt /data/blockscout-dev-private/v10-candidates/candidate-fya6fuzs/candidate.json
python3 deploy/scripts/v10_upgrade.py --prepare \
  --private-file /data/blockscout-dev-private/private-20261103.json \
  --receipt /data/blockscout-dev-private/v10-candidates/candidate-fya6fuzs/candidate.json
```

Check repeats the live review and verifies NFT worker numeric identity and mount
access. Prepare then saves a private journal under
`/data/blockscout-dev-private/v10-upgrades/upgrade-.../state.json`, with modes
0700/0600. It freezes the forward/previous Compose models, original container
metadata, exact image, environment, migration inventory and executable migration
script. The previous Compose file is evidence for manual recovery; it is not an
automatic post-schema rollback path.

An isolated candidate client verifies its real database route against the
inspected PostgreSQL container. It starts only dependencies and repositories,
checks PostgreSQL 15, active repository routes, every compiled migration hash,
actual applied versions, heap identity, selected column types/table presence,
smaller relation sizes and selected background status records. This phase runs
no migrations and does not stop or start application services. Environment and
connection values go through private stdin/files, not command-line arguments.

Preparation must return `v10_upgrade_prepared`. Retain its exact `state` path.
Do not copy the journal or private logs out of the server.

## Apply the saved plan

Set `upgrade_state` to the actual path reported above:

```bash
upgrade_state=/data/blockscout-dev-private/v10-upgrades/upgrade-REPLACE/state.json
python3 deploy/scripts/v10_upgrade.py --apply --state "$upgrade_state"
python3 deploy/scripts/v10_upgrade.py --status --state "$upgrade_state"
```

Apply acquires the shared deployment/storage locks, disables the old pair's
restart policies, stops the NFT worker and then backend with their recorded grace periods (five
minutes when unspecified), and repeats the
candidate database checks with those clients stopped. PostgreSQL, Redis, stats,
frontend, proxy and other services remain running. Their container identities,
images, definitions, mounts and original running states are checked throughout.
The two init services remain stopped.

Before launching a writer, the journal durably records that schema writes may
have started. The isolated migration client uses the frozen image/script and
requires the original database identity, baseline versions, internal-transaction
heap and selected background records to match. A dedicated PostgreSQL connection
holds an advisory lock across repositories. Every connection has a two-second
lock timeout and a 120-second statement timeout; the complete client has a
30-minute limit. Logs stay private.

The runner applies main versions only through `20260220073250`, then account
through `20251029115930` and Arbitrum through `20250731001757`. It checks the
actual executed set. The custom versions `20260721000000` and `20260812000000`
remain unapplied; none is manually stamped complete. It verifies that the large
internal-transactions heap identity and selected background records are unchanged.
The runner never invokes broad `create_and_migrate` or an all-versions migration.

The shared filesystem is sampled once per second while the writer runs. The
runner stops its own client if free space falls below 100 GiB or consumption
since the first write attempt exceeds 20 GiB. These are operational thresholds,
not a hard filesystem quota. The budget requires smaller affected relations
below 1 GiB and at least 120 GiB free before writes; it does not cover historical
backfills or heavy indexes. An interruption during schema work leaves the old pair stopped, with
its restart policies disabled, until explicit resume or manual recovery.

After schema verification, Compose recreates only `backend` and
`nft_media_handler` using the same pinned v10 image, preserved mounts, ports,
network aliases/cookie and the producer's preserved `/folder_1`. Both start with
`bin/blockscout start` and an explicit background-migration hold. No startup
migration command runs. Verification checks actual application version, readiness,
representative APIs, ETH price cache/policy, history/code/scanner settings, absence
of automatic migration children and the NFT queue protocol/folder. The NFT check
observes connected nodes without using `Node.ping` to establish a connection.

Expected result: `verified`, `recorded_phase=active`. Current chain/indexing
progress still needs observation after activation. Large normalization/index/PK
work remains a separate measured operation; do not remove its startup hold.

## Status, retry and the recovery boundary

```bash
python3 deploy/scripts/v10_upgrade.py --status --state "$upgrade_state"
python3 deploy/scripts/v10_upgrade.py --resume --state "$upgrade_state"
```

Status reads the journal/current service metadata and probes an activated pair.
Resume stops/removes only an orphan schema client owned by that journal, uses the
same frozen artifact and reads actual applied versions. A partial schema attempt
executes only remaining reviewed versions. Activation retries recreate only the
pair and do not rerun successful schema work. Missing members during a recorded
Compose recreation are supported. A successful active plan is verified without
migration or recreation on another resume.

Before `schema_writes_may_have_started=true`, `--abort` can restart the original
containers and restore their policies:

```bash
python3 deploy/scripts/v10_upgrade.py --abort --state "$upgrade_state"
```

After that flag is set, abort refuses to start v9. A failed writer may have
committed earlier schema versions or a nontransactional queue change. An image
switch cannot undo that work. The supported automatic retry uses the same v10
artifact; any return to v9 requires the operator's manual database recovery.
The old normal release rollback helper cannot load this separate journal format
or overwrite the newly owned pair.

The normal `deploy.sh dev plan` recognizes this upgrade's forward snapshot and
image/environment overrides. It still exposes subsequent source image or runtime
override changes. Normal candidate builds retain their source/profile version
guard; promoting the public v9 profile to the stable v10 build policy is a later
change after live validation.

## Local validation

`deploy/tests/check_v10_upgrade.py` uses disposable PostgreSQL 15, Redis and a
local RPC stub on an internal network, without host mounts or public ports. It
recreates v9 with synthetic rows, rejects database-route/migration-file drift,
deliberately blocks the account-table drop after the 26 main versions, retries
only the remaining two account/one Arbitrum versions, and repeats with zero more
executions. It preserves the nonempty heap and completed historical-reindex
record while leaving both custom versions pending.

The same fixture starts full backend and standalone NFT applications, checks the
actual startup hold and automatic peer connection, and reads representative
blocks, transactions, tokens and transaction internal-traces APIs. Block fetching
is paused in this fixture; real RPC/market availability, live volume permissions,
large-database duration and full-size backfill cost are outside its scope.

Unit checks cover private snapshot replay, schema-write journaling before client
launch, stopped-pair preservation on failure, refusal of v9 abort after writes,
space-triggered owned-client cleanup, pre-write abort, partial-pair activation
retry, upgrade/legacy format separation and visibility of later source changes.
