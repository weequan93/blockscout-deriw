# Hold the empty-block sanitizer during dev normalization

The live diagnostic at 2026-11-04 18:54:50 SGT (10:54:50 UTC) found a 477-second
snapshot query from the `backend` container. Its MD5 was
`f7d49ed68ea1ac040431775d295eaae5`, with 310 bytes of SQL. Reconstructing the
denormalized branch of
`Indexer.Fetcher.EmptyBlocksSanitizer.unprocessed_empty_blocks_list_query/1`
with the compiled v10 query planner produces exactly that MD5 and byte length.
The query selects candidate blocks and tests for absent transactions, with a
LIMIT and no lower block-number bound. A small returned-row limit does not bound
the work needed to find those rows. No live EXPLAIN ANALYZE or history scan was
requested for this investigation.

The sanitizer is a regular indexer fetcher. The migration-autostart flag and
the existing `Indexer.Prometheus.Metrics` hold do not stop it. This operation
pauses only its GenServer child under
`Indexer.Fetcher.EmptyBlocksSanitizer.Supervisor`. The parent supervisor, its
task supervisor and the other `Indexer.Supervisor` children are verified across
the operation. The backend container, live indexer, API and NFT supervisors
retain their deployment identities.

The paused work includes empty-block repair scans and subsequent block/refetch
bookkeeping. Already committed bookkeeping remains. An in-flight attempt may be
interrupted. Restore starts sanitization immediately and may perform database
updates and configured block RPC calls as part of the normal fetcher.

## Apply the scoped hold

Push the reviewed tooling commit and check it out on the explorer server, then:

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_empty_blocks_hold.py --hold \
  --upgrade-state /data/blockscout-dev-private/v10-upgrades/upgrade-20261104T032739Z-96b06eb3/state.json
```

Preparation observes the current worker and resolves at most one active matching
query on the frozen backend connection addresses, same database and role, with
no assigned XID. Multiple matches stop for review. If the previous query has
already finished, a worker-only hold prevents the next scheduled scan. There is
no need to chase a copied PID. Optional `--pid` and `--query-start` must be given
together; a stale target never permits cancellation.

The tool saves private inputs, the compiled-query fingerprint, backend runtime
identity and the exact RPC source in a new journal under
`/data/blockscout-dev-private/v10-empty-blocks-holds/hold-.../state.json`.
It durably records `hold_requested` before changing the supervised child.
Worker shutdown is bounded by its reviewed child specification, at most five
seconds. If the original SELECT outlives its owner, cancellation rechecks PID,
backend start, query start, MD5, backend connection address, database, role,
active state and absence of an assigned XID in the same SQL statement. It never
terminates a database session or cancels a changed/foreign query.

The controller makes no node calls or explicit data updates. It preserves
migration completion records, the existing metrics hold, normalization cursor,
pending snapshots, row/WAL/storage budgets and the accepted manual recovery
policy. This is a runtime hold; restarting the worker's parent or the backend
can re-enable the sanitizer. Persistent environment and compose files are
unchanged.

## Observe, recover and restore

```bash
python3 deploy/scripts/v10_empty_blocks_hold.py --status --state HOLD_STATE
python3 deploy/scripts/v10_empty_blocks_hold.py --resume --state HOLD_STATE
python3 deploy/scripts/v10_empty_blocks_hold.py --restore --state HOLD_STATE
```

`--status` is observation only and may use current tooling. Runtime changes use
the hold's creation commit and frozen RPC source. A lost hold response remains
`hold_requested`; status and resume reconcile it without stopping another child.
Restore is idempotent and starts only this worker with its existing child spec,
on the same pinned backend deployment. Keep the older metrics-hold journal
separately; restoring this worker does not restore metrics.

After the hold verifies, reconcile the pending normalization session from its
own creation commit `346cb91636a942269027cbe7e2b140b3b9730bc5`:

```bash
python3 deploy/scripts/v10_normalization_session.py --resume \
  --state /data/blockscout-dev-private/v10-normalization-sessions/session-20261104T102826Z-a94b3044/state.json
```

That session started at 18:28:26 SGT and retains its original 30-minute write
window. Expiry prevents another update; it can reconcile unchanged pending rows
and finish without advancing the cursor. Retain the journal. Only a finished,
non-pending session can serve as a predecessor for another observation epoch.
New epochs inherit the maintenance baseline and the already charged selected-row
phase allowance; the 300-second client-transaction guard remains unchanged.

lost-response reconciliation, idempotent hold/restore, stale targets, ambiguous

PostgreSQL 15 check starts the actual compiled sanitizer under its normal
