# Finite dev normalization run

The v10 application is active. The initial one-row pilot, two individual batches
and two finite runs have verified 25,144 normalized stored rows. The latest
run applied 18,347 rows in 19 batches and finished at its minimum WAL allowance
limit, with no pending child. No application restart, historical RPC or migration completion record
occurred. Global normalization, reindex and heavy index/PK workers remain held.

The finite controller can continue at most 25 of the same bounded batches in
one invocation. It is a small workload pilot, not authorization to traverse the
full 1.78-billion-row table. Each batch commits separately. A later stop retains
all earlier verified commits and a pending child journal for recovery.

## Run from the latest verified batch

Use the committed tooling revision provided with the run command:

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_normalization_run.py --run \
  --after-state /data/blockscout-dev-private/v10-normalization/batch-20261104T071440Z-46553c32/state.json \
  --max-batches 25 --max-rows 25000
```

The command verifies the starting batch, saves a private run journal and prints
its limits before sampling or updating additional rows. `--prepare` saves only
the run inputs; `--resume --state RUN_STATE` can execute that saved run later.
Inputs include the source revision, initial journal digest, image, client digest,
limits and initial free-space observation. Resume must use the creation revision.
The ten-minute start window begins at preparation; later reconciliation remains
available, but fresh updates require an unexpired window.

For each chunk it performs the existing indexed 1,001-row sample, excludes an
ambiguous tail block and retains at most 1,000 rows in complete blocks. Its first
cursor is strictly below the latest verified block `132038224`, leaving any
previously excluded boundary block eligible. It freezes a full row snapshot and the
same compiled-callback client. The new child pointer is durably recorded before
any update. After transaction and runtime verification it records the child and
advances the cursor to that child's oldest complete block.

## Limits and observations

The operator must provide both batch and selected-row limits. They cannot exceed
25 batches or 25,000 selected rows. A whole next batch that would exceed the
remaining row allowance is left unapplied; the controller does not split blocks.
Each transaction keeps the previous 1,000-row/16 MiB snapshot cap, 500-ms lock
acquisition, five-second statements, ten-second pre-commit checks and 60-second
client limit. The callback's lock-query plan must use the approved block-number
index. Original row hashes, semantics, schema versions and selected migration
records are checked as in the [single-batch runbook](v10.2.6-normalization-pilot.md).

The run allocates a total of 128 MiB to the sum of measured chunk WAL windows.
Each new child receives only the unspent part of that budget, enforced inside
its transaction. A WAL-limit failure rolls back that child. If a commit response
was lost and its WAL measurement was not saved, reconciliation charges the
child's whole allowance. This prevents another update from using an unknown
remaining budget. It does not estimate WAL produced between chunks or in final
commit records; concurrent cluster writers contribute to measured windows.
New runs also require at least 16 MiB of allowance before starting another
batch, stopping normally with `next_batch_wal_reserve_reached` if less remains.
This is a minimum starting allowance, not a guarantee that 16 MiB stays unused.
It can finish before reaching 25 batches or 25,000 rows. Existing frozen runs
retain their original limits and remain readable without the new reserve field.

All children share the same initial free-space observation. The existing host
guard requires at least 200 GiB free and at most 512 MiB observed net consumption
from that run's starting observation. Unrelated writers contribute to filesystem
changes. New updates also stop after a ten-minute start window. Reconciliation
of a committed child can finish after that window without another data update.

Output includes each child's state path, selected/updated rows, cursor, elapsed
time, WAL measurement and conservative charge, plus observed data free space.
Rows, credentials and SQL remain private. These are limited observations and do
not qualify the full table's WAL, bloat, vacuum or historical-backfill budget.

## Status and recovery

Copy the run state path printed before the first chunk:

```bash
python3 deploy/scripts/v10_normalization_run.py --status \
  --state /data/blockscout-dev-private/v10-normalization-runs/run-REPLACE/state.json
python3 deploy/scripts/v10_normalization_run.py --resume \
  --state /data/blockscout-dev-private/v10-normalization-runs/run-REPLACE/state.json
```

Status verifies the recorded last batch and observes any pending child. It does
not kill a running client or write data. Resume uses the recorded pending child
before creating another sample. A committed result is reconciled without a
second update, including when the parent checkpoint response was lost. An
active owned client is reported for observation rather than replaced. Preserve
all samples, child journals and the run directory.

A finished run stays finished on resume; its limits cannot be reset or enlarged.
An exhausted sampled range, oversized leading block, changed rows/status,
unsupported query plan or resource limit never stamps global completion or
starts dependent workers. An empty non-null range below the cursor also does not
cover null block numbers or later inserts. The reported last verified child is
the starting point for separately reviewing further work.

## Validation

Unit cases cover durable cursor advancement, lower child WAL limits, a shared
space baseline, timeout rollback, lost commit/checkpoint responses, conservative
WAL charging, row/time caps, frozen-input changes, client observation and a
finished resume. They also exercise 25 consecutive controller batches, the new
minimum starting allowance and legacy frozen inputs. The isolated PostgreSQL 15 fixture uses the actual normalization
clients and queries for five 1,000-row transactions, verifies boundary inclusion
and remaining older work, and repeats the finished controller without updates.
Host release/health metadata is stubbed only in this disposable fixture; it does
not access live services.

The read-only report observed 6,797 updates, of which 121 (about 1.78%) were HOT,
and an estimated 6,765 dead tuples. No vacuum/analyze activity was recorded in
the current statistics and no vacuum was in progress. The catalog row estimate
remains 1,776,221,184; the statistics view's zero live-row counter does not mean
the table is empty. No table-specific vacuum or fillfactor override was present.

Autovacuum and count tracking are enabled, with vacuum threshold 50 and scale
factor 0.2. The regular update/delete vacuum trigger is therefore approximately
`50 + 0.2 * 1776221184 = 355244286.8` dead tuples, using PostgreSQL's catalog
estimate. Other vacuum triggers exist. See the
[PostgreSQL 15 autovacuum formula](https://www.postgresql.org/docs/15/routine-vacuuming.html#AUTOVACUUM).
Full-table execution needs a separate vacuum, indexing and journal-retention
plan; this finite pilot does not establish that capacity.

The report found no replication slots or slot-retained WAL, with archive mode
off. Full-page writes are on and WAL compression is off. `max_wal_size` is
1,024 MiB; this is a checkpoint target rather than a disk-usage hard limit
([PostgreSQL WAL configuration](https://www.postgresql.org/docs/15/wal-configuration.html)).
The existing measured WAL and host free-space guards remain necessary.

The expanded pilot retains the 128 MiB measured chunk WAL budget, 512 MiB net
space guard, 200 GiB remaining-free floor and ten-minute start window. Its
per-transaction row, snapshot, time, query-plan and semantic checks are unchanged.
Only new runs may request the larger 25-batch/25,000-row ceiling. It does not
change vacuum settings, create indexes, refresh global completion records or
start any held background worker.
