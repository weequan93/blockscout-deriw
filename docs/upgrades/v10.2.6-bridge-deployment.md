# Deploy the bridge cursor correction during native normalization

The application source change is exactly the reviewed
`NewMessagesToL2.check_historical/1` correction from
`427661a011f635a0d6852570b09abdc910c6c727`. The release branch merges that commit
with the persistent native-normalization tooling. It adds no schema migration,
index build, conversion SQL or database completion stamp.

The server still runs application source
`f8119a0a2f65593d184be66a57480660e3663b25`. Public observation on November 6
confirmed deposits 325–328 have completion transactions but lack parent-chain
transaction/block/timestamp metadata. Source checkout alone cannot replace the
compiled application image.

## One deployment command

Use a separate clean checkout for the release. Leave
`/data/blockscout-v10-rehearsal` at the existing native job's creation commit.
After fetching and checking out the published release commit under
`/data/blockscout-v10-bridge-rehearsal`, run:

```bash
python3 deploy/scripts/v10_bridge_deploy.py --run --normalization-state /data/blockscout-dev-private/v10-native-normalization/job-20261106T103901Z-59bb4dc6/state.json
```

Keep that terminal connected until the command finishes. It prints build
progress and the private release state path. Repeating the same command selects
the existing journal rather than creating another deployment. The original
normalization job is paused during the build and rollout.

The command performs these steps:

1. Stop the exact owned normalization service and confirm its writer exited.
   Preserve all original inputs, worker source, DB metadata, cursor and budgets.
2. Freeze the live deployment, environment, database identity, schema versions,
   heap identity and native migration record in a private journal.
3. Build a committed AMD64 v10 image with automatic migrators disabled. Require
   identical migration files and numeric runtime identity, only the two reviewed
   custom migrations pending, and successful isolated release-config checks.
4. Save forward and rollback Compose snapshots. Recreate only `backend` with
   `bin/blockscout start`, without schema migrations. PostgreSQL, Redis, stats,
   frontend, proxy and the existing NFT worker remain in place.
5. Reapply the reviewed metrics and empty-block sanitizer holds to the new
   backend. Verify readiness, runtime settings, held migrators, NFT connectivity,
   chain identity and unchanged schema/heap/native checkpoint.
6. Write a separate immutable runtime-binding receipt beside the existing native
   job. Update its systemd controller to the release checkout, retaining its
   original native image, token, frozen worker and saved database cursor. Start
   that same normalization service after releasing deployment locks.

There is no new cumulative disk-growth cap. Existing native thresholds and
transaction guards remain. The initial build needs 220 GiB data free and 10 GiB
root free. Old upgrade, vacuum, hold and normalization journals are not rebased.

## Status and recovery

Use the printed release state path for a read-only review or an interrupted run:

```bash
python3 deploy/scripts/v10_bridge_deploy.py --status --state /data/.../state.json
python3 deploy/scripts/v10_bridge_deploy.py --resume --state /data/.../state.json
```

Resume uses the frozen source/image/environment and does not rerun database
migrations. It can reuse a fully built, correctly fingerprinted image. Failed
verification leaves native normalization paused at its saved checkpoint.
An image switch is not automatic recovery from an unreviewed schema change.

After the successful handoff, use the release checkout for native controls:

```bash
python3 deploy/scripts/v10_native_normalization.py --status --state /data/blockscout-dev-private/v10-native-normalization/job-20261106T103901Z-59bb4dc6/state.json
systemctl is-active blockscout-v10-native-normalization.service
```

The old native checkout remains available as evidence. Its systemd definition is
saved privately before replacement. The new binding accepts only the exact
verified bridge release and unchanged native frozen inputs. A subsequent
deployment or modified release journal invalidates that binding for further work.

The bridge tracker is reinitialized by the new backend. Its cursor must be
observed advancing, and deposits 325–328 must regain their origination metadata,
before declaring the display issue resolved. The existing 50-block request range
and 10-second interval are unchanged; deploying the fix does not establish an ETA
or prove that the tracker has already caught up.

## Validation

The five bridge ExUnit regressions run in a local container without network or
database access. Deployment unit tests cover the exact source boundary, backend
only snapshots, checkpoint-preserving binding, refusal of failed/changed release
proofs, service ownership, journaling before recreation, restored holds and
database identity checks. Existing release and native-normalization tests remain
part of the validation suite. The server build and live verification still run
before activation is accepted.
