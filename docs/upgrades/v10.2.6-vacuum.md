## One monitored window

`deploy/scripts/v10_vacuum.py` executes this fixed command on one dedicated
connection outside a transaction:

```sql
VACUUM (VERBOSE, INDEX_CLEANUP ON, TRUNCATE OFF, PARALLEL 0)
  public.internal_transactions
```

Connection-local settings are 512 MB maintenance memory, vacuum cost limit
200, cost delay 2 ms, lock timeout 500 ms and statement timeout one hour.
The client also has a one-hour duration ceiling. No table/global settings or
migration completion records change. Ordinary vacuum permits normal table
access and makes existing space reusable; filesystem shrinkage is not a success
criterion. See [PostgreSQL 15 VACUUM](https://www.postgresql.org/docs/15/sql-vacuum.html).

The window retains a 200 GiB free-space floor; at most 4 GiB net filesystem,
table or retained-WAL growth; 16 GiB observed cluster WAL; and 2 TiB observed
relation shared-buffer reads. Measurements include concurrent work and
statistics lag. Shared-buffer misses do not measure physical bandwidth or
latency; cost delay provides pacing. Cleaning roughly 988 GB of indexes may
exceed the window. An interrupted cycle cannot qualify completion.

Preparation requires a finished normalization review checkpoint, both hold
journals, the active upgrade and original runtime/database/heap identity. It
verifies the normalized anchor, schema versions and all five migration records,
including absent records. It refuses active/pending normalization, another
target-table vacuum, client transactions over 300 seconds, prepared transactions
and replication slots retaining an xmin. Preparation only reads the database.

After pushing and checking out the reviewed tooling commit:

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_vacuum.py --run \
  --after-session /data/blockscout-dev-private/v10-normalization-sessions/session-20261104T123253Z-520c10b3/state.json \

  --empty-blocks-hold /data/blockscout-dev-private/v10-empty-blocks-holds/hold-20261104T115233Z-cb796fca/state.json
```

`--prepare` with the same arguments saves only a reviewed plan. A prepared
window must start within ten minutes. `--resume --state VACUUM_STATE` starts
a still-prepared window or monitors/reconciles its single requested execution.
After launch is requested, resume never launches another vacuum. Keep the shell
running during observation; interruption triggers the watchdog.

## Identity, monitoring and recovery

The observer code and checkpoint hashes cross Docker stdin into a temporary
0600 file in the existing backend. The short RPC expression evaluates that
file and returns `:ok`; a shell trap removes the file on success or failure.
No hash lists or credentials enter command-line arguments. A full checkpoint
would otherwise exceed the 128 KiB single-argument limit on 4 KiB-page Linux
hosts. The regression verifies an actual 1,000-row normalized anchor and checks
temporary-file permissions and cleanup. See the kernel's
[MAX_ARG_STRLEN definition](https://github.com/torvalds/linux/blob/master/include/uapi/linux/binfmts.h).

Before dispatch the tool durably records the dedicated PID, backend start,
database/role OID, unique application name, fixed statement fingerprint and
effective settings. It saves `vacuum_requested` before publishing the start.
The host polls every ten seconds and renews a lease only after successful
health/runtime/resource checks. An observation gap over 30 seconds stops the
window and removes only its image/label-verified maintenance container.

The independent client watchdog exits the isolated VM after 45 seconds without
a newer lease. A frozen token and increasing sequence reject lease replay.
This closes only its maintenance socket. Connection-local
`client_connection_check_interval=1s` lets PostgreSQL detect the closed socket
during a command; the one-hour server statement timeout remains a separate
limit if network failure delays disconnect detection. No foreign database
session is signalled. See the [connection check setting](https://www.postgresql.org/docs/15/runtime-config-connection.html#GUC-CLIENT-CONNECTION-CHECK-INTERVAL).

Only the exact maintenance PID/backend-start/application identity is excluded
from client transaction observations. Every observation checks both runtime
holds. Progress records heap scanning/vacuuming and index-vacuum passes through
[pg_stat_progress_vacuum](https://www.postgresql.org/docs/15/progress-reporting.html#VACUUM-PROGRESS-REPORTING).

New windows freeze `transaction_guard_scope=pre_vacuum_clients` outside the
unchanged limits dictionary. Before the actual vacuum statement is observed,
all other clients retain the 300-second guard. The tool then verifies the
owned PID/backend-start/application/role and exact statement fingerprint in
`pg_stat_activity`, saves its server `query_start` as private `vacuum-start.json`
and pins that proof's hash in state. An active statement or the same socket's
idle last VACUUM command can provide the timestamp. SQL completion still
requires its separate successful receipt.

During that window, clients whose transaction started at or before this proved
boundary retain the 300-second rejection rule. Later transactions remain in the
reported maximum age and query diagnostics; their age alone does not cancel
the current vacuum. PostgreSQL establishes its removable-tuple cutoff before
scanning the heap and uses that cutoff for index/heap cleanup. A reader starting
later does not invalidate the already selected dead tuple IDs. See the
[PostgreSQL 15 heap vacuum cutoff and cleanup sequence](https://github.com/postgres/postgres/blob/REL_15_STABLE/src/backend/access/heap/vacuumlazy.c).

Prepared transactions, replication xmin, health/identity, duration, WAL,
filesystem and read-growth checks remain enforced. Normalization's own
all-client age guard is unchanged. Old vacuum journals retain their original
all-client behavior; no old timestamp or budget is edited. The later-client
observations must still be reviewed before subsequent normalization begins.

Each read-only observer also records up to 20 client transactions older than
60 seconds: fingerprints, snapshot/wait metadata, known source-template matches
and service candidates. It suppresses SQL, row values and client addresses.
The owned vacuum is filtered by PID and backend start. Observations, including
the one that rejects a window, are saved before resource guards run. Public
status and resource failures retain these details, avoiding a race with a
transaction that finishes before a later manual diagnosis.

`--status --state VACUUM_STATE` reads the saved journal without a maintenance
lock or database call, including during execution. It does not prove current
database state. Resume uses the creation commit and frozen inputs. A missing
or failed receipt never counts as completion or authorizes automatic relaunch.
Interrupted vacuum can leave useful partial cleanup. Finished windows retain
their original duration and budgets.

Preparation failures report a safe exception type and source file/line/function
locations. Existing privacy-safe `ConfigError` messages remain visible, with an
OS errno when available. Other exception messages and stack source/values stay
suppressed. The first live attempt at source `67454c811` returned a generic error
with no journal path; it never reached execution. The large-checkpoint transport
fix preserves the command, limits, worker holds and normalization review gate.

## Retention and completion review

Private journals under `/data/blockscout-dev-private/v10-vacuum/` retain frozen
inputs/sources, the original normalization checkpoint identity and accounting,
before/latest/after resource reports, timestamped observations and the client
log containing the VERBOSE result and completion receipt. Files are 0600 and
directories 0700. Each journal is capped at 64 MiB, its log at 16 MiB and all
vacuum journals at 256 MiB. Preparation reserves a full journal and inventories
at most 32 entries before requiring manual retention review. No legacy or new
journal is deleted or compacted by this tool.

`vacuum_sql_completed=true` requires a matching receipt for this fixed command.
`completion_verified=true` also requires fresh runtime, normalized-anchor,
migration-record and resource checks, plus confirmation the socket has gone.
The normalization gate stays closed in both cases. Review the VERBOSE index
cleanup, completed phases, vacuum counters, dead-row reduction, WAL/storage/I/O
and service behavior. A bounded later update interval must demonstrate space
reuse before sustained pacing or table-specific vacuum policy is selected.
No global worker or heavy index/PK operation is enabled.

## Validation

Unit checks cover the review gate, frozen inputs, accounting, pending writes,
ownership/settings, stale health, resource ceilings, receipts and no-relaunch
recovery. The disposable PG15 fixture completes the actual ordinary vacuum,
checks effective local settings, counter/VERBOSE evidence and preserved anchor
and migration records, and rejects appearance of an absent migration record.
A delayed fixture statement loses its lease and stops while a foreign advisory
lock survives. The fixture also keeps a real repeatable-read snapshot from
before the proved VACUUM start and opens another afterward. It briefly delays
receipt publication after the fixture VACUUM to make the server timestamp
proof deterministic. One-second comparison thresholds are used only in the
fixture's policy checks: the old snapshot is rejected, while a later snapshot
is reported and the legacy all-client guard still rejects it. The production
limits remain unchanged. Host application health/runtime are stubbed; a
completed live cycle and space recycling remain unmeasured.
