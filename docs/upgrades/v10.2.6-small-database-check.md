# Small-database migration check — 2026-11-03

The real v9.0.1 and prepared v10.2.6 releases passed a local migration sequence on
PostgreSQL 15.19 with synthetic data. This verifies the 31 migration versions
reported pending by the dev server. It is separate from the required restore and
full-size rehearsal of the 4.575 TiB database.

No existing database or deployment was accessed. The test created an internal
Docker network with no published ports and no host mounts. PostgreSQL used tmpfs
storage. Only dependency applications and the three Repo processes were started
for release evaluation; the Blockscout application, indexer, RPC fetchers and
automatic background migrators were not started. All test containers and the
network were removed afterward.

| --- | ---: | ---: | ---: | --- |
| Recreate v9 baseline | 294 | 26 | 7 | 28 main + 2 account + 1 Arbitrum |

| Run v10 migrations again | 0 | 0 | 0 | Zero in all three repositories |

The source has 27 account migration files, but one historical version,
`20221104104635`, creates the same token-ID progress table in both main and
account repositories. With these repositories sharing a database, main executes
that version first; account therefore executes 26 additional versions. This does
not change the two new account versions pending for the candidate.

The baseline deliberately left the two custom index versions unapplied, matching
the server output. The candidate executed those two versions along with the 29
new upstream versions across the active repositories. One new account version
is a schema no-op on Arbitrum, but is still recorded as applied by Ecto.

Synthetic checks passed after both the upgrade and repeat run:

* The pending transaction and its generated method ID survived.
* Both token metadata-reset migrations changed eligible rows and retained
  unrelated partial-metadata and false rows.
* Legacy proxy rows were reset as intended; the unrelated proxy was retained and
  enum labels were renamed.
* Signed authorization chain IDs widened to `numeric(78,0)` and accepted a value
  larger than a signed 64-bit integer.
* The existing contract ABI survived the uniqueness-index replacement, and a
  duplicate insert still raised the expected unique violation.
* Account public-tag removal, queue creation/removal, sanitizer-status resets,
  new unvalidated internal-transaction constraints and the Arbitrum EigenDA enum
  change matched the migration definitions.
* All six indexes in the two previously deferred custom migrations were valid
  and ready after execution on the fixture.

## Repeat the check

With the matching baseline and candidate images already built locally:

```bash
python3 deploy/tests/check_upgrade_database.py \
  --baseline-image deriw-blockscout:v9-upgrade-baseline \
  --candidate-image deriw-blockscout:v10-upgrade-local-validation \
  --postgres-image postgres:15-alpine
```

The command accepts image references only. It creates its own synthetic database
credentials and network; it accepts no database destination or server env file.
It checks PostgreSQL major version 15 and verifies the test database destination
before migrating. Detailed version lists and logs are saved in a new temporary
directory shown in the output. The final stdout summary omits the long baseline
version list.

When building test images, pass an **absolute Dockerfile path** corresponding to
the chosen source context. A relative `-f docker/Dockerfile` can resolve from the
calling checkout instead of the other context. Set the release version to 9.0.1
for the baseline or 10.2.6 for the candidate and select `CHAIN_TYPE=arbitrum`.
Do not use the regular dev deployment helper to bypass its version guard.

## Limits and remaining deployment requirements

The fixture did not restore the dev backup and contains no real chain data. The
large logs/internal-transactions/export-queue tables are empty. No background
backfill, internal-transaction primary-key transition, production API/UI/NFT
startup, full-size index build, migration-duration or peak-space measurement was
performed. The local fast timings are not estimates for the live database.

The user-reported main database is 5,030,129,032,551 bytes, with only 959 GiB free
on `/data` and no separate rehearsal storage currently available. A full restore
still needs a suitable separate destination and a verified recovery procedure.
Keep the repaired v9 deployment active until those checks pass; these local
results do not authorize applying the candidate to that database.
