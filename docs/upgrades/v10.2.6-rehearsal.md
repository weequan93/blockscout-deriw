# Deriw Blockscout v10.2.6 preparation

This branch prepares the first stage of `9.0.1 → 10.2.6 → 11.3.3 → 12.0.4`.
It does not authorize a live upgrade or establish that the existing database can
be migrated within an acceptable window. Keep the repaired v9 dev release active
until a restored-database rehearsal has passed.

## Reconciled behavior

The seven initial conflict files are resolved against the v10 implementations.
The following policies remain part of this fork:

* Strict receipt identity validation and the Arbitrum missing-receipt fallback.
  Upstream's optional receipt-by-block dispatch remains available. The default
  is `ETHEREUM_JSONRPC_RECEIPTS_BY_BLOCK=false`; keep that value explicit for the
  first rehearsal so batches take the validated custom fallback path. Enabling
  upstream's direct block-receipt path requires its own response tests.
* Contract-code concurrency 1 and a 60-second retry, with bounded historical work.
* Trace range `176114083..latest`, the old-block revert lookup guard, and cached
  revert rendering. Upstream moved revert fetching from `Chain` into
  `Chain.Transaction`; a compatibility delegate retains existing release checks.
  Transaction/first-trace RPC dispatch now also filters this range, covering the
  new on-demand fetcher. Missing trace data stays unavailable; no fabricated
  success or historical completeness is recorded.
* The old temporary historical token scanner remains opt-in and off by default.
  v10.2.6 still uses that scanner. The later v11/v12 replacement must be reviewed
  separately; this flag will not automatically govern a differently named worker.
* Approximate transaction counts remain enabled through the local flag. The
  later upstream equivalent has not been introduced into this v10 stage.
* Arbitrum confirmation ordering and the bounded token-transfer anti-join remain
  aligned with the existing indexes. Empty-block checks use block number and
  consensus only after transaction denormalization; they retain the hash fallback
  beforehand and upstream's newer locking structure.
* Advanced filtering uses upstream's rewritten query pipeline, retaining the
  exclusion of internal-transaction queries when that fetcher is disabled. The
  legacy SQL logging and top-50 transaction-hash restriction were replaced.
  Measure the replacement's plans and pagination on the restored database.
* ETH price-only mode retains price/history while withholding Ethereum supply,
  market cap and volume from dev native-coin figures. It uses v10's coin cache.
* Six custom main-repo migration files and their versions are preserved, including
  the generated method ID and the two deliberately deferred index migrations.
  A schema-changing rehearsal must review those deferred migrations explicitly;
  they are not an implicit part of the v10 approval.

The public profiles, proxy stats repair, pinned verifier-list configuration,
private-input handling and normal release/rollback safeguards remain in the
repository. Test/prod need their own inventories and rehearsal records.
The frontend and microservice images are unchanged in this stage.

## Read-only server evidence

First push this integration branch from the local checkout. On the explorer
server, use a separate checkout, leaving `/data/blockscout` and the active review
checkout intact:

```bash
git -C /data/blockscout fetch origin upgrade/blockscout-v10.2.6
git -C /data/blockscout worktree add --detach \
  /data/blockscout-v10-rehearsal origin/upgrade/blockscout-v10.2.6
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/upgrade_plan.py
python3 deploy/scripts/upgrade_plan.py --live
```

These commands create source files and read the existing backend's metadata.
They do not build an image, start an app or create a container. `--live` uses the
running release's existing Repo connections to read schema versions and two
selected background-status records with short read-only transactions. It checks
dev's chain identity from container metadata and checks container stability
before/after. Raw environment values and SQL errors are suppressed.

The command always reports `deployment_permitted: false`. A missing background
record means “not recorded”, not “completed”. The required primary-key status
for moving onward to v11 is `heavy_indexes_create_internal_transactions_pkey`.
It is expected to become relevant during the v10 rehearsal; its absence on v9
does not alone prevent beginning the rehearsal. These two status records do not
constitute a complete audit of all background work.

## Database restore and migration rehearsal

1. Record current database topology, PostgreSQL version/extensions, applied schema
   versions, background statuses, database/index sizes and available storage.
   Inventory every actual database behind the configured main/account/Arbitrum
   repositories; some may share a destination. Record the currently active image
   IDs, exact frontend/microservice versions, Compose configuration, mounts and
   Nginx files. Keep env files and release/private-input directories server-only.

2. Choose a consistent backup and recovery method for that topology. Rehearse
   restoring it with the matching PostgreSQL major version on **separate storage**.
   For a physical snapshot/base backup, preserve the required WAL through its
   recovery target and verify recovery completes. An online `cp`/`rsync` of the
   live data directory is not a consistent backup. Prove that the restored v9
   application can read the clone before applying any v10 change.

3. Create a dedicated rehearsal network, new database/container names and empty
   target data paths. Do not attach the clone to the live Compose network or
   mount any live database, DETS, log or NFT worker directory. Use rehearsal
   credentials with access only to the clone, no live credentials, mail/webhooks,
   exporter or external writer destinations. Initial migration containers must
   have no route to the live database. Record the restored backup identity.

4. Build the pinned integration revision for the **server's architecture** from
   a clean committed archive. Set `CHAIN_TYPE=arbitrum`, `RELEASE_VERSION=10.2.6`
   and `BLOCKSCOUT_VERSION` to that integration commit. Record image ID, platform,
   build arguments and migration hashes in a rehearsal receipt. Local ARM64
   compilation is validation, not an AMD64 deployment artifact. Do not relabel a
   v9 receipt or use the regular dev deployment helper to bypass version checks.

5. Derive the pending migration set from the clone's actual schema versions and
   the candidate files. Review destructive/locking work, especially account
   public-tag removal, proxy-implementation changes, contract-method uniqueness,
   internal-transaction constraints/queues and the conditional `VACUUM FULL`
   operations on export queues. Review all six custom migrations, including the
   two deferred indexes, and resolve their handling before executing the release
   migration task. Never mark versions applied without executing/verifying the
   corresponding schema change. Preserve and measure already-applied history.

6. Run the reviewed v10 migrations **only on the clone**, with application
   startup separate from migration execution. Capture timing, lock waits, I/O,
   WAL growth, temporary/index space and peak free space. No universal timeout
   or capacity threshold is assumed from the old server observations. Abort at
   agreed storage/lock thresholds and practice recovering the clone from the
   backup. Establish the production window from measured results.

7. Review automatic application-start background workers before starting v10.
   `bin/blockscout start` avoids Ecto startup migrations but does not suppress
   background migrators. Rehearse structural backfills, constraint validation and
   primary-key replacement. Do not indiscriminately disable them: v11 requires
   the primary-key transition to complete. Keep trace-history limits, pending
   fetcher disabled, internal-transaction indexing disabled and the temporary
   token scanner disabled as in current dev. Structural work may still be needed
   even when that fetcher is disabled. Measure it rather than stamping it done.

8. Enable only the deliberately selected read-only dev RPC routes for a bounded
   indexing test. Verify progress, reorg handling, receipts, latest and historical
   transaction pages, logs, token transfers, address tabs, advanced-filter
   pagination, transaction stats, cached revert reasons, unavailable-history
   behavior and gas/USD formatting. Confirm the custom frontend, stats proxy and
   smart-contract verifier work. Test the upgraded NFT app/worker pair with
   rehearsal-owned storage and queue; the local source tests do not establish
   cross-version NFT compatibility. Keep real outbound integrations isolated.

9. Write an evidence record with backup/restore timings, exact pending/applied
   versions, completed and incomplete background jobs, query plans/latencies,
   API examples, resource peaks and the chosen recovery window. The next v11
   stage can be prepared after the v10 primary-key prerequisite is proven. v12
   later requires its own address-ID backfill and frontend/microservice API review.

An image-only rollback is suitable for the existing same-version deployments,
not a database recovery plan after this upgrade. Rehearse restoring the pre-v10
database and bringing up its pinned v9 application, including how post-upgrade
chain indexing will be caught up. Do not assume schema-down migrations are safe
or that a v9 image can operate on a database after v10 structural backfills.

## Local validation

Run each Python suite separately because their dynamic-module fixtures share
names. The focused ExUnit runner uses a compiled builder image and never starts
the applications or a database:

```bash
python3 -m unittest discover -s deploy/tests -p test_upgrade_plan.py
python3 deploy/tests/check_upgrade_repairs.py --image deriw-blockscout:v10-upgrade-compile
```

The compilation/release generation and focused tests do not replace the restored
database rehearsal, AMD64 candidate build, full application tests, real query
measurements or UI/NFT interoperability checks. No live metadata, migration,
backup or deployment was performed from this local preparation.
