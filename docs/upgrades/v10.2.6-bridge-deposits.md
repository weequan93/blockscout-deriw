# Bridge deposits missing parent-chain metadata

The deposits page can show a relayed message and a completion transaction while
its parent-chain block, transaction and timestamp remain absent. The rollup
transaction importer records completion independently of the parent-chain bridge
message tracker. On DeriW these are the L3 completion and L2 origination fields.

## Historical completion can stall live discovery

`NewMessagesToL2.check_historical/1` stops when its next block is below the
configured `l1_rollup_init_block`. Previously, that completion path also replaced
the historical cursor with `l1_rollup_init_block - 1`. If previously indexed
messages predate that configured floor, this moves the cursor forward, potentially
beyond the live discovery cursor.

Live discovery excludes the historical range but calculates its end from the
live cursor plus the configured block range. The result can be an empty range
on every iteration, leaving the tracker alive and enabled without advancing.

The server observations on 2026-11-05 at 09:57:19 and 09:57:49 SGT showed:

| Field | Both observations |
| --- | ---: |
| Next parent block | 278124097 |
| Historical boundary | 286461006 |
| Blocks per request | 50 |
| Recheck interval | 10000 ms |
| Queued batches | 1 |

Both catchup tasks were marked complete. The historical boundary forces the next
start to at least 286461007, while the calculated end is at most 278124146.
No log query can run for that inverted range. Messages 325–328 were missing
origination metadata in the public API; their L3 completion transactions existed.

The correction preserves the existing historical cursor when marking the task
complete. It leaves live cursor advancement, reorg overlap, RPC range limits,
and the configured historical floor in place. It does not skip the intervening
parent blocks or mark missing message metadata complete.

## Validation

The five ExUnit tests cover historical completion with older known messages,
continued live discovery across consecutive empty ranges, the last historical
chunk, overlap with unsafe blocks, and waiting at the chain head. The original
worker fails the two regressions; the corrected worker passes all five.

Run them without database or network access using an existing local compile
image containing the project dependencies, Elixir and Mox:

```bash
python3 deploy/tests/check_arbitrum_message_cursor.py
```

The runner resolves the local image ID, streams the current worker and tests into
a disposable container, compiles the worker and runs the ExUnit tests. It uses
no host mounts and does not start the indexer application.

## Deployment and verification

This is compiled application code. Checking out a tooling commit on the server
does not update the running worker. An already affected process also retains its
inverted cursors until it is reinitialized through a reviewed activation plan.

Keep the current monitored vacuum window and its pinned checkout intact. A backend
restart releases runtime-only maintenance holds. Prepare the corrected candidate
and activation plan separately, and activate it after the vacuum window has been
reconciled. Enabling general background migrations does not repair this cursor.

After activation, compare the tracker cursor across observations and review its
parent-chain RPC results. The existing small block range and recheck interval can
still leave substantial catchup work; successful cursor repair alone does not
establish a completion time. Verify origination metadata for messages 325–328
through the deposits API before declaring the display issue resolved.
