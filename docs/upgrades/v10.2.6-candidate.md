# Build the dev v10 candidate without deployment

The operator completed containerd relocation and source archival/cleanup. The
2026-11-04 read-only preflight confirmed PostgreSQL 15.18, a 5,032,581,356,903-byte
main database, about 31 GiB root space and 898 GiB on the shared data/WAL disk.
There are no replication slots. On 2026-11-04 the operator explicitly accepted
manual, unverified recovery. `snapshot_verified` remains false; collecting
snapshot evidence is not an approval gate. The schema working-space budget is
separate from both that decision and the later historical backfills.

The dedicated `v10_candidate.py` helper builds from a clean committed Git
archive. It requires the captured dev chain `18417507517`, current v9.0.1
backend, unchanged live runtime model, reviewed migration inventory, completed
storage retirement and the AMD64 platform. It preserves the regular deployment
helper's v9 source/profile guard. The public dev Compose profile stays on v9.

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_candidate.py --check \
  --private-file /data/blockscout-dev-private/private-20261103.json
python3 deploy/scripts/v10_candidate.py --build \
  --private-file /data/blockscout-dev-private/private-20261103.json
```

Check creates no image, container or candidate directory. Build creates an
upgrade-specific image/tag and private candidate receipt under
`/data/blockscout-dev-private/v10-candidates`. It never invokes Compose up, app
start or migration commands. Private values enter only isolated release-config
evals over stdin, outside the committed build context. The eval containers have
no network or host mounts and use a read-only filesystem with temporary scratch.
The exact source, build arguments, migration hash, image ID and baseline service
images are recorded. Logs and receipts remain private on the server.

Expected result: `v10_candidate_verified`, with `activation_performed=false` and
`deployment_permitted=false`. A repeat check reports whether that exact tag
exists; use `--build --reuse` to revalidate an existing matching candidate.
The helper does not overwrite an existing candidate without that explicit mode.

## Hold automatic background migrations

The candidate is built with `MIGRATION_BACKGROUND_AUTOSTART_DISABLED=true` in
its image environment. Runtime configuration selects
`Explorer.Migrator.StartupControl`, which filters automatic `Explorer.Migrator.*`
and the legacy token-owner migration supervisor from Explorer's startup children.
Repository children, the migration-status cache, normal indexing processes and
existing database completion records remain available. This includes holding
internal-transaction normalization, historical reindexing and heavy index/PK
workers. It does not disable Ecto schema migrations, stop already running
workers or prevent explicitly supervised maintenance work.

Normal builds default this flag to false, preserving upstream startup behavior.
The v10 helper requires its candidate to inherit true and rejects a captured
runtime profile that overrides this value. Its isolated evals verify the hold,
the five selected migration workers, pending-operation switch and preservation
of Repo/status-cache children, alongside scanner unset/false/true cases and
existing history, code-retry, transaction-count and ETH price policies.

The build's 10 GiB root / 150 GiB data free-space floors cover build preparation
only. They do not establish the budget for the estimated 1.78-billion-row
internal-transactions backfill. Hold removal and live schema/data changes need
the separate controlled migration/recovery procedure. A verified image is not
deployment authorization or a database recovery point.

## Preserve the completed storage audit

Building a candidate legitimately adds image/tag bindings to Docker. The old
storage-maintenance record preserves its exact pre-build image inventory and
can subsequently report `image_bindings_changed`. Do not rewrite its saved
inventory. This candidate helper checks the original service identities/images,
mounts, target configuration, archived-source receipt, empty source directory
and actual backend overlay on `/data/containerd` directly before/after building.
Its receipt captures the current build baseline separately. A future application
deployment must capture a fresh lifecycle baseline.

This validation covers a committed build and release configuration. Full v10
application startup, API compatibility, migration execution and background
worker cost remain later steps.

The local compiled-module/release checks can be repeated against matching native
validation images with:

```bash
python3 deploy/tests/check_upgrade_repairs.py \
  --image deriw-blockscout:v10-nft-compile \
  --runtime-image deriw-blockscout:v10-nft-local-validation \
  --background-migrations-held
```

This checks the exact held-candidate expressions with scanner unset/false/true,
and separately verifies explicit opt-out in the real release configuration.
Native ARM64 validation images are local test artifacts; the server still needs
its own committed AMD64 candidate and receipt.

## Upgrade both NFT roles

The v9 producer sends a URL list; the v10 producer sends `{urls, producer_folder}`.
The v9 worker cannot consume that new reply. Both `backend` and
`nft_media_handler` must therefore use the same v10 candidate. Preserve the old
worker map's `/folder_1` on the producer using
`NFT_MEDIA_HANDLER_BUCKET_FOLDER=/folder_1`; existing media paths must not change.

The v10 worker discovers connected nodes rather than consulting the legacy map.
For this static Docker deployment, runtime configuration converts the validated
legacy map keys into an EPMD libcluster topology. A five-second reconnect period
keeps the worker attached after a backend restart. This topology is enabled only
for the remote standalone worker. Cookies remain private and unchanged.

Candidate validation checks both roles, the static producer peer, reconnect
configuration and preserved producer folder. The local distributed test uses
two real release VMs, an internal disposable network and the actual v10 queue
and consumer. It verifies automatic discovery, reconnect and producer-supplied
folder selection without an application tree, database or public port:

```bash
python3 deploy/tests/check_v10_nft_peers.py
```
