# Dev v10 in-place upgrade preparation — 2026-11-03

The user selected an in-place upgrade because separate full-size rehearsal
storage is unavailable. The user reports that a recent Tencent Cloud snapshot
exists, but its ID, timestamp, covered disks and consistency are not yet known.
These facts select the preparation route; they do not establish a usable recovery
point, an adequate working-space budget or a completed live upgrade.

The current v9 backend remains active. This document is the staged operational
plan, not an apply command. The normal same-version deployment helper retains
its version/migration checks and must not be relaxed to activate this upgrade.

The live storage reads subsequently confirmed the containerd image store while
the root filesystem has only about 1.3 GiB free. Prepare the separate
[containerd storage-maintenance plan](containerd-dev-storage-plan.md) before
building the server candidate. Docker's `/data/docker` setting alone does not
move containerd's image store.

## Confirm storage and recovery

Run the new read-only command from the updated separate source checkout:

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/upgrade_plan.py --in-place-preflight
```

It reads PostgreSQL 15 server metadata, selected WAL settings, replication-slot
counts, external tablespace locations and sizes of tables touched by the pending
migrations. The existing backend Repo connection must match the inspected `db`
container's address on a shared network. The helper then resolves the data, WAL
and external tablespace paths with `readlink` in that container and maps them
through the longest matching Docker mount. Host `stat`/`statvfs` provide capacity
without scanning database directories. It also reports root filesystem capacity
to help choose a location for upgrade state outside the disks being restored.
The query uses `host(inet_server_addr())` for this comparison: casting PostgreSQL's
`inet` value to text includes a network mask such as `/32`, while Docker's
inspected address has no mask.

All SQL runs in one read-only transaction, with 1.5-second statements, 500-ms lock
waits and a five-second transaction limit. Docker metadata and path reads are
bounded separately. Raw credentials, URLs, Docker env/command values, archive
commands, replication-slot names and network addresses are not exported.
If a check fails, the command reports fixed `stage` and `error_kind` labels.
SQL failures distinguish permission, timeout/cancellation, lock and schema
errors without exporting SQL error detail or connection values. A failed probe
does not establish that the upgrade or a database mutation was attempted.

Important interpretations:

* Matching filesystem device IDs mean shared capacity; do not add their free
  space. Different filesystem IDs do not prove different cloud disks.
* Unmapped/container-layer storage or an unavailable host path must be resolved
  before choosing snapshot disks.
* A repository with a different connection configuration needs topology review;
  that difference does not alone prove a separate server.
* PostgreSQL `max_wal_size` is not a hard bound on retained WAL. Snapshot coverage
  also does not establish enough live working space for a backfill.
* Snapshot identification remains an operator/cloud-console step. The command
  does not contact Tencent Cloud or mark a snapshot verified.

Record the snapshot ID, source disk IDs, creation/completion time with timezone,
status and whether PostgreSQL/VM was running or stopped. Match its source disks
to the resolved data, WAL and tablespace placement. A running-database snapshot
needs a consistent point across all of those files and the required WAL. A
properly coordinated snapshot can be usable without a cold shutdown; do not
assume any arbitrary collection of disk snapshots is consistent. If the existing
snapshot cannot be established as suitable, prepare a fresh pre-upgrade backup
in the maintenance procedure. No live stop or snapshot operation is performed
by this preflight.

Restoring an older recovery point loses database changes since that point,
including off-chain account/verification data that chain RPC cannot recreate.
Confirm that recovery point and the provider's rollback procedure before writes.
A cloud snapshot is distinct from allocating a second restore disk; choosing
in-place avoids the full rehearsal copy but does not make recovery evidence
unnecessary.

## Staged rollout to prepare after the evidence is collected

1. **Retain the current release.** Save exact image IDs, runtime/private inputs,
   Compose project/network/mount configuration and Nginx configuration. Keep
   private copies and the upgrade journal outside any volume that rollback will
   replace. Preserve ownership/modes. A saved configuration or image is not a
   database backup.

2. **Build the server-architecture candidate.** Build the pinned v10 application
   from a clean committed archive, record its image/source identities and verify
   runtime settings. Local ARM64 tests do not substitute for the server artifact.
   Test startup with automatic data backfills held before replacing the backend;
   a standard application start can launch Explorer background migrators even
   when the internal-transaction fetcher is disabled.

3. **Set the maintenance and recovery boundary.** Before schema changes, verify
   the backup/snapshot procedure, covered disks, rollback steps and recovery point
   with the operator. Pause the relevant writers during the approved procedure.
   Snapshot rollback may involve stopping the VM and replacing more than the
   backend database if multiple services share the disk. Record that impact.

4. **Apply the 29 new upstream migration versions separately from app startup.**
   The proposed initial sequence is 26 main-repo versions through
   `20260220073250`, two account versions and one Arbitrum version. Leave the
   two existing custom versions, `20260721000000` and `20260812000000`, unapplied.
   This defers their six indexes; do not delete their files or stamp them applied.
   The new number-based unique internal-transaction index is separate background
   work and is not one of these six optional deferred indexes.

5. **Start and validate v10 with data backfills controlled.** Confirm backend
   readiness, selected API responses, NFT connectivity, USD price policy, current
   indexing behavior and missing-history guards. Existing completed
   `reindex_duplicated_internal_transactions` status is preserved; upstream skips
   rerunning that worker while the record remains completed. An image-only
   rollback must not be used as database recovery after step 4.

6. **Run required structural work in measured stages.** Start with low concurrency
   and small block batches for `EmptyInternalTransactionsData`, monitoring WAL,
   filesystem free space, locks, transaction duration and application health.
   Its batch identifiers are block numbers, not a guaranteed row limit. The
   estimated 1.78-billion-row dataset has not been rehearsed at full size. Select
   and implement pause/free-space thresholds and a recovery response before the
   live run; do not assume 959 GiB free is a sufficient budget. Then complete the
   unique index, constraint validation and primary-key swap, checking real
   catalog state and worker records after each stage.

7. **Observe before later upgrades.** Confirm application compatibility and
   indexing progress. Keep optional custom indexes deferred until their costs are
   separately reviewed. Proceed to v11 preparation only after the real v10
   primary-key prerequisite is complete; a completion record does not prove
   queued historical traces were recovered.

The candidate hold/control, maintenance/apply/restore commands, server build,
working-space thresholds and full application tests remain to be finalized.
There is no in-place `--apply` operation in the preflight helper. This plan does
not infer permission to stop the database from a request to collect metadata.

## Local evidence for the staged sequence

```bash
python3 deploy/tests/check_upgrade_database.py --background --defer-indexes
```

The disposable PostgreSQL 15 fixture passed this sequence: 29 new upstream
versions applied, the same two custom versions remained pending, a repeat run
applied zero more, and the five selected background workers completed their
tested normalization/primary-key work. Synthetic assertions confirmed that the
six custom indexes were not built in this path. The new PostgreSQL metadata
probe also ran on the fixture's v9 and v10 databases. Storage/path mapping and
output filtering have separate unit tests.
The fixture compares the actual PostgreSQL connection address and port with the
inspected PostgreSQL container on its isolated network, without exporting those
addresses in the result.

These tests do not establish live migration duration, data distribution, peak
space, full application startup, cloud snapshot consistency or successful
restoration of the real database.
