# Select a small v10 normalization batch

The initial v10 code/schema upgrade is active. The refreshed server metadata
still estimates 1,776,221,184 internal transactions, a 592,414,932,992-byte heap
and 1,598,637,326,336 bytes including indexes/TOAST. The data filesystem has
888 GiB free. The old `(block_hash, block_index)` primary key and all ten reported
indexes remain valid/ready. Normalization, the new unique index, not-null
validation and the primary-key swap are not recorded complete. The existing
historical-reindex record remains `completed` and must be preserved.

## Read-only candidate selection

Run from the updated, clean upgrade checkout:

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_normalization_plan.py \
  --upgrade-state /data/blockscout-dev-private/v10-upgrades/upgrade-20261104T032739Z-96b06eb3/state.json
```

This uses the existing backend Repo, requires the active paired v10 image and
background startup hold, and verifies that the five selected workers are absent.
The helper starts no container or worker and makes no database changes.

It checks for a valid, ready, nonpartial index starting with `block_number` and
requires index access paths before running either trace query. The first query
seeks the newest stored internal-transaction block with `ORDER BY ... LIMIT 1`.
The second reads at most 1,001 rows from that block in the existing index order.
It reports how many sampled rows need normalization and their PostgreSQL row-size
estimates. It also reads selected table-update/autovacuum counters, cluster WAL
counters and existing migration states. No trace values, URLs, credentials or
raw query plans are exported.

All reads run in one read-only transaction with 1.5-second statements, a 500-ms
lock limit and a five-second transaction limit. `EXPLAIN` inspects plans without
executing them. The transaction temporarily discourages sequential scans; it
still rejects a sequential/bitmap scan, sort or missing approved index before
executing either trace query. That preference ends with the transaction.

A pilot candidate requires a complete block of at most 1,000 rows, at most
16 MiB in estimated row bytes, some normalization work, at least 200 GiB data
free, the preserved completed historical-reindex record and no heavy index job
recorded started. The helper returns blockers if those conditions fail. Size
estimates and global counters do not establish the update's WAL or space cost.
`apply_available=false` is deliberate: this command only selects the workload.

## Why the full worker stays held

The upstream worker's initial search is `max(block_number)` with the full
unprocessed-row predicate and an unlimited timeout. Its batches count block
numbers, not rows. Starting it with a small batch setting does not bound that
initial search or the number of traces in one busy block. The read-only helper
avoids that initialization path.

After collecting the real candidate, prepare a separate one-block update using
the actual compiled `EmptyInternalTransactionsData.update_batch/1` callback,
with a hard SQL time limit, drift checks, WAL/free-space limits and semantic
verification. Measure elapsed time, changed rows, WAL and disk consumption while
preserving the application's hold. A one-block pilot must not mark the full
normalization completed or start dependent unique-index/PK workers. Its observed
cost will guide a resumable larger-stage budget; it is not a full-size rehearsal.

The user's manual, unverified recovery decision remains recorded. No new
snapshot confirmation is required to prepare this stage.

## Selected live candidate and executable pilot

The server selected block `171635973`: one stored row, one row needing
normalization, 324 estimated row bytes, valid index-only/index access paths and
952,993,935,360 bytes free. This block is older than the configured RPC trace
floor `176114083`. The pilot transforms stored data and makes no historical
trace request; it does not recover the missing newer/older trace history.

The new `v10_normalization_pilot.py` tool runs the compiled v10
`EmptyInternalTransactionsData.update_batch([block])` callback directly. It does
not start the GenServer, invoke the initial unbounded search, advance the global
normalization cursor, write a completion record, refresh the completion cache,
start dependent workers or recreate the application containers.

After updating the clean upgrade checkout, run:

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_normalization_pilot.py --run \
  --upgrade-state /data/blockscout-dev-private/v10-upgrades/upgrade-20261104T032739Z-96b06eb3/state.json \
  --block 171635973 --expected-rows 1
```

`--run` first repeats the active-release health and indexed workload checks,
saves an immutable script and the full original bounded row snapshot privately
under `/data/blockscout-dev-private/v10-normalization/pilot-...`, and prints the
prepared plan with transformation counts. It then applies that same saved plan.
For a separate preparation step, use `--prepare` with the same arguments, followed
by `--apply --state <reported pilot state>`.

Both stages use the pinned image and private runtime inputs from the active
upgrade journal. A disposable client starts only the Repo/dependencies. SQL
verifies the database identity, exact applied schema versions, original heap
identity, selected worker states and an approved index plan. Preparation uses a
read-only transaction; raw snapshots and logs stay in 0700/0600 server-only files.
No credentials or row values enter CLI arguments or public JSON.

The write transaction acquires the shared PostgreSQL maintenance advisory lock
and a `SHARE ROW EXCLUSIVE` lock on internal transactions. That lock briefly
blocks other writers to this table while ordinary readers can continue. The
500-ms acquisition limit avoids waiting behind existing writers/DDL. It prevents
new rows from expanding the selected block between the count check and the real
callback. Every statement has a five-second limit, the transaction must finish
its checks within ten seconds before commit, and the client has a 60-second wall
limit. At most 1,000 rows/16 MiB can be selected; this invocation requires exactly
one row.

Before the callback, current full-row fingerprints must match the saved
snapshot. After it, all selected rows must be normalized and their canonical
semantic fingerprints must match: nonzero values, effective call types/error
messages/destinations and all other columns are preserved. Zero values become
NULL, errors move to the lookup table, call types move to the enum, created
contract destinations are filled, and legacy trace paths are intentionally
cleared according to upstream behavior. The original row remains in the private
snapshot for operator-managed recovery. Migration records must remain identical.

The callback and verification share one transaction. A before-commit WAL delta
above 256 MiB or a failed invariant rolls back row/error-table changes. The WAL
delta includes concurrent cluster writers and excludes the final commit record;
rolling back does not erase generated WAL or sequence allocations. The host
monitor requires 200 GiB free and stops only its owned client if observed data
filesystem consumption exceeds 512 MiB. A process interruption is reconciled
against the saved original/normalized fingerprints; an observed committed result
is not updated again. Metrics are saved before subsequent application health
checks so that a lost response can be investigated.

Expected result: `status=verified`, `updated_rows=1`, and zero remaining work in
this selected block. Global migration status remains unchanged. This tiny test
establishes functional behavior and a first cost observation; it cannot predict
the duration or space cost of 1.78 billion rows.

Use the reported pilot state for later observation/retry:

```bash

```

Status does not interrupt a running client. Resume reconciles actual row data
before any further update and preserves the same script, image, workload and
limits. The operator's existing manual recovery decision continues to apply.

The exact callback test additionally verifies rollback after a deliberately
exceeded WAL limit, row-count/full-row drift rejection, idempotent repeats,
nonzero values, error relocation and created-contract destinations. Full backend
and standalone-worker startup/API checks pass with legacy and normalized rows
mixed while the global completion record remains absent:

## Recover the first batch's statement timeout

The first live batch attempt used journal
`batch-20261104T045554Z-f77a66ea`. Its client failed with a PostgreSQL statement
timeout. Read-only status subsequently returned `not_applied`, with all 959 rows
still matching the complete original snapshot and all migration records unchanged.
The application was not restarted and global migration workers remain held.

A disposable planner test reproduces a failure mode of the old client: applying
`enable_sort=off` to the callback as well as snapshot reads can make PostgreSQL
walk the entire transaction-hash index to satisfy the callback's ordering. With
statistics modelling 1.78 billion rows and rare selected blocks, restoring normal
sort planning changes that unrestricted scan to a block-number index seek and
a sort of selected rows. This is a reproduced planner issue; the live log
classification alone identifies a statement timeout, not its precise query plan.

The corrected client permits the callback's sort and checks its lock-query plan
before execution. Original failed journals keep their frozen clients. Use a new,
linked journal to apply the corrected client while retaining the exact original
rows and targets:

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_normalization_batch_update.py --retry \
  --state /data/blockscout-dev-private/v10-normalization/batch-20261104T045554Z-f77a66ea/state.json
```

Retry first observes the original journal and requires an unchanged `not_applied`
result. It copies the original sample, row snapshot and parent state into a new
private journal, freezes the corrected client and verifies its read-only plan and
the original full/semantic row hashes. It then prints the new state path, bounded
callback plan and prepared workload before applying that same journal. The parent
state/client remain unchanged. A changed parent state, row, count or release input
stops the retry. `--prepare-retry` performs only the preparation and plan checks;
`--apply --state NEW_STATE` can apply it later. Subsequent status/resume commands
must use the newly printed state path.

The five-second statement, 500-ms lock, ten-second pre-commit, 60-second client,
256 MiB observed WAL, 200 GiB remaining-free and 512 MiB consumption checks are
retained. No recovery snapshot, index build, completion record or global worker
start is added. Client failures now identify the last allowlisted stage while
keeping SQL, parameters and original rows in private logs.

The updated PostgreSQL fixture checks the planner regression using catalog
statistics changed only inside its disposable database. It also forces a real
five-second statement cancellation during the 959-row callback and verifies
rollback of every selected row and error insert before a successful retry.
Unit checks verify linked-journal preservation, original-row drift rejection,
already-committed rejection and safe failure-stage reporting.
