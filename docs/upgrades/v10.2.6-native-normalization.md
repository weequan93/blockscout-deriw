# Persistent native normalization

**Installed and handed off to the bridge release on 6 November 2026.** Use the
[current operations guide](../deployment/dev-v10.md) for the active checkout,
saved state and commands. The one-time installation below is historical setup;
do not prepare a second job or change either pinned source checkout.

The v10.2.6 application and reviewed schema migrations are already deployed.
Historical `internal_transactions` rows still need data conversion. This job uses
`Explorer.Migrator.FillingMigration` for batching and durable database checkpoints,
and calls the original `Explorer.Migrator.EmptyInternalTransactionsData.update_batch/1`
for each conversion. It does not reimplement the conversion SQL.

Global background startup remains disabled because enabling it also starts other
migrators. Only this normalization worker runs, in a separate container using the
already pinned v10 image. The backend is not restarted. Duplicate reindex,
unique-index creation, NOT NULL validation and primary-key changes remain separate.

## Disk policy and automatic cleanup

There is **no cumulative disk-growth cap**, no finite phase allowance and no
overall job deadline. DevOps may add disk capacity while the job is paused. The
original maintenance baseline and old journals remain intact; their old budgets
are not rewritten or reused as new allowances.

New batches pause below 210 GiB free and resume at 220 GiB. Preparation requires
at least 200 GiB free. These margins allow an in-flight bounded transaction to
finish; concurrent services also consume disk, so this is not a filesystem quota.

The worker sets only these options on `public.internal_transactions`:

| Option | Value |
| --- | --- |
| `autovacuum_vacuum_scale_factor` | 0 |
| `autovacuum_vacuum_threshold` | 5,000,000 |
| `autovacuum_vacuum_cost_limit` | 400 |
| `autovacuum_vacuum_cost_delay` | 2 ms |

PostgreSQL schedules routine vacuum cleanup. The controller pauses writes when
the estimated dead-row count exceeds 10 million and waits for cleanup. It also
waits on failed health probes, client transactions older than 300 seconds, or
disabled autovacuum. Ordinary vacuum makes space reusable within relations;
it generally does not shrink the files. No periodic manual vacuum commands are
needed for this job. The table options remain after completion.

## Checkpoints and interruption

The immutable handoff is:

- Finished session: `session-20261106T013658Z-66761f68`, strictly below block
  **131385496**, with no pending transaction.
- Qualified vacuum: `vacuum-20261106T054009Z-9fa91730`, completed and verified.

The native metadata starts at `max_block_number=131385495`. Each successful native
batch checkpoints the next cursor in the existing `migrations_status` record for
`empty_internal_transactions_data`, together with a unique job token. Restarting
the same job preserves this metadata. Exclusive reservations beside both old
journals prevent a second job from consuming the handoff.

The native callback is idempotent. If conversion commits but cursor persistence
is interrupted, the same blocks are replayed safely. A final read-only residual
check covers the entire table, including NULL blocks and rows above the transferred
cursor, before the native framework may mark the migration completed. A residual
row stops completion for review.

There is one writer. Native batches initially cover 1,000 block numbers, with
adaptive reduction down to one block. Each transaction permits at most 10,000
sampled rows, 16 MiB sampled row data and 128 MiB observed cluster WAL, with a
30-second SQL timeout and 500 ms lock timeout. Exceeding a bound rolls back and
reduces the block range. A single block exceeding the bounds requires review;
it is never skipped. Known transient database errors retry at most five times
without cursor progress. The final residual check has a four-hour read-only
timeout.

A token-bound host lease expires within 30 seconds. A disconnected controller
therefore stops authorization for further batches. Waiting happens outside a
database transaction. A dedicated database advisory lock prevents a second
worker for this job. The controller keeps bounded private worker diagnostics.

Systemd restarts a crashed controller and reattaches its owned running worker.
It retains progress after a process, container or host interruption. Runtime
identity and the two existing worker holds must still pass before more work is
authorized. A backend restart loses those in-memory holds and requires review
and restoration before the saved job can continue. Changed images, containers,
configuration, database identity or source checkout also require review; this
job does not rebind itself to another deployment.

## One-time installation

Publish the committed `maintenance/v10-native-normalization` branch from the
development checkout, then fetch and check out the reviewed commit on the server.
Use the exact commit supplied with the change, and keep the rehearsal checkout
there while the service is enabled.

```bash
cd /data/blockscout-v10-rehearsal
python3 deploy/scripts/v10_native_normalization.py --run \
  --after-session /data/blockscout-dev-private/v10-normalization-sessions/session-20261106T013658Z-66761f68/state.json \
  --after-vacuum /data/blockscout-dev-private/v10-vacuum/vacuum-20261106T054009Z-9fa91730/state.json
```

`--run` prepares and reserves the handoff, then installs and enables
`blockscout-v10-native-normalization.service`. It prints the new private job
`state.json` path. The service continues after the terminal disconnects and
starts on boot. Its policy and worker source are frozen in that job directory.
No backend deployment, source build, or all-migrator startup is performed.

If setup stops after printing `native_inputs_saved`, retain that printed state
path and use `--install-service --state /data/.../state.json`. The same job can
finish a partial reservation pair; do not prepare another job.

## Optional status and controls

Replace `/data/.../state.json` with the printed native job path:

```bash
python3 deploy/scripts/v10_native_normalization.py --status --state /data/.../state.json
python3 deploy/scripts/v10_native_normalization.py --pause --state /data/.../state.json
python3 deploy/scripts/v10_native_normalization.py --start --state /data/.../state.json
```

Status reads saved files and reports the last observation, descending native
cursor, disk space, worker phase and any waiting reason. It does not scan rows to
estimate a percentage or ETA. `waiting` is automatic and needs no manual resume
after low space or health recovers. `paused` requires `--start`.
`needs_attention` requires fixing its stated problem and then `--start` on the
same job. Never delete the state directory or migration metadata to restart.

The controller emits its public result when it stops. Systemd considers
`needs_attention` exit code 2 a review stop and does not restart it repeatedly.
Use `systemctl status blockscout-v10-native-normalization.service` for service
state. `normalization_complete=true` means the native data migration and final
residual check completed; it does not mean every deferred index/PK migration has
been applied.

## Local validation

`test_v10_native_normalization.py` exercises frozen inputs, reservation recovery,
disk hysteresis, cursor ownership, batch reduction, bounded retries, completion,
container ownership and service configuration. The disposable PG15 fixture
`check_v10_native_normalization.py` runs the actual compiled native framework and
callback, interrupts between data commit and cursor persistence, verifies replay
without duplicate updates, rejects residual rows, and then reaches completion.
It accesses no live services.
