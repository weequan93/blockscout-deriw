background data migrations are deliberately held by

were verified. This implementation supplies a reusable client, short transactions,

## Reduce preparation overhead

New sessions can explicitly select `--execution-profile lean-v1` independently
of their limit profile. This changes batch preparation and preserves every
row/time/WAL/storage/health limit, the original maintenance baseline, the
vacuum review gate and checkpoint retention. Sessions without this flag keep
the original execution path; a saved session cannot change execution profiles
during resume. Select it explicitly again when preparing a successor.

A fresh batch requiring an update uses four mailbox requests instead of seven:

1. `prepare_batch` combines the existing read-only resource report, indexed
   sample and baseline inspection. Each transaction closes before the next.
2. A separate fresh resource check still precedes the write.
3. The host requests the unchanged compiled update callback only after saving
   and fsyncing the complete raw baseline and pending target. The write
   transaction rechecks row counts, exact hashes, semantics, query plans,
   database/heap/schema/migration identity and health before UPDATE.
4. A resource observation follows the transaction before advancing the cursor.

The fresh baseline replaces the additional host-side reconciliation inspection.
After any interruption, an existing pending target always gets a new inspection;
unknown commit outcomes are reconciled without another update, and unknown WAL
still consumes the entire remaining allowance. All waits for the host remain
outside transactions. The command returns raw baseline rows only through the
existing private mailbox/journal transport.

On an eligible finished predecessor, preparation syntax is:

```bash
python3 deploy/scripts/v10_normalization_session.py --prepare \
  --after-session FINISHED_ELIGIBLE_STATE \
  --profile observation-v1 \
  --execution-profile lean-v1
```

The current journal `session-20261104T123253Z-520c10b3` stopped at the vacuum

## Transactions and vacuum

One isolated container and Repo are reused for the finite execution. Commands
cross a private mailbox using container stdin/stdout, without host bind mounts,
application volumes or credentials in shell arguments. The client exits after
60 seconds idle or 200 requests. Every wait for the host occurs outside a
database transaction; there is no snapshot held while the host fsyncs a journal
or checks service readiness.

The sampler reads at most 1,001 rows below the cursor through the block-number
index. It excludes every row of an ambiguous boundary block. An oversized first
block stops without skipping it. The write transaction verifies at most 1,000
rows and 16 MiB of row data, checks the callback plan, and invokes the compiled
`EmptyInternalTransactionsData.update_batch/1` implementation. The upstream
error relocation, effective call type/value/destination and other columns are
verified before commit.

New session writes use **REPEATABLE READ**, replacing the pilot's explicit
`SHARE ROW EXCLUSIVE` table lock. The fixed transaction snapshot bounds the
callback's visible block contents. The normal row/table locks used by its
SELECT FOR UPDATE and UPDATE permit ordinary vacuum's SHARE UPDATE EXCLUSIVE
lock. Concurrent updates to selected rows can abort the transaction with a
serialization failure; no automatic overwrite or unlimited retry occurs.
See [PostgreSQL snapshot semantics](https://www.postgresql.org/docs/15/transaction-iso.html#XACT-REPEATABLE-READ)
and the [lock compatibility table](https://www.postgresql.org/docs/15/explicit-locking.html#LOCKING-TABLES).

An insert committed after the transaction snapshot is invisible to that
transaction. It may consequently sit behind the stored-data cursor. A changed
row count/semantic result during later reconciliation stops the tool. This is
one reason cursor exhaustion cannot stamp global completion: a separate residual
review must cover concurrent inserts, null block numbers and upstream completion
semantics. Historical RPC and missing-trace recovery remain separate work.

Statements retain five-second timeouts, lock acquisition 500 ms, and transaction
checks ten seconds. Before issuing DML the script also validates a host health
deadline of at most 30 seconds. New sessions freeze a 15-second start reserve:
the host renews readiness evidence once it is 15 seconds old, leaving time for
dispatch and bounded SQL prechecks before UPDATE. The SQL deadline stays at
30 seconds. A delayed request can still expire and roll back; it returns the
specific `health_freshness_before_update` reason. Failed replies remain readable
for ten seconds outside any transaction, so the host can collect the reason
before the disposable client exits. Runtime identity is checked around every
write. All automatic migrators and migration status/cache records remain held.

## Execution and storage budgets

The default legacy profile retains the 25-batch/25,000-row ceiling, 128 MiB sum of measured
chunk WAL windows, 16 MiB minimum remaining allowance for another batch,
512 MiB net filesystem consumption cap and 200 GiB remaining-free floor.
Each transaction receives only the remaining WAL allowance. Unknown committed
WAL consumes that whole allowance and stops further writes. Measurements include
concurrent cluster writers but exclude final commit records and gaps between
the measured chunk windows; they are not a retained-WAL or full-table forecast.

Before and after transactions, additional guards stop on more than 512 MiB
growth in table/index allocation, WAL directory size or slot-retained WAL,
more than 100,000 additional estimated dead rows, an absolute dead-row estimate
above one million, statistics resets, disabled autovacuum/count tracking, or a
client transaction older than 300 seconds. An autovacuum worker is excluded
from the client-transaction duration guard so a long vacuum can continue.
No session is terminated and no database setting is changed automatically.

The private `resources-before.json` and overwritten `resources-latest.json`
contain measurements and counter deltas. Counters include other sessions and
may lag. They establish neither physical bloat nor a complete capacity forecast.
Saved per-session limits cannot be enlarged from the command line. A new session
may select one of the fixed versioned profiles below.

## Diagnose an old or rejected session

```bash
python3 deploy/scripts/v10_normalization_session.py --diagnose --state SESSION_STATE
```

This reads the saved evidence/current free space and collects metadata in one
bounded read-only transaction through the existing backend Repo. It starts no containers,
changes no session journal and performs no normalization, cancellation or restart.
It remains available when a historical session's 512 MiB consumption allowance
is exceeded. A backend metadata failure still returns the filesystem evidence.

Output separates current free space from consumption since the saved baseline,
and the saved transaction observation from the current backend observation.
Transaction details include up to 20 oldest client transactions over 300 seconds,
their PIDs, state, snapshot/XID presence, waits, classified application kind and
observer role OID/visibility. SQL, usernames, addresses and raw application names
are not printed. New preparations freeze the same metadata query, retaining these
details at the point a guard stops them; old frozen scripts retain their original
aggregate-only observations.

The current diagnosis also captures up to 20 client transactions older than
60 seconds in that same database observation, so a query can be identified
before it reaches the write guard. `query_diagnostics` includes backend/query
start times, SQL MD5, SELECT/WITH classification, a fixed set of aggregate
fingerprints and mentioned table names. The observer compiles a few known Ecto
count/sum queries to SQL for exact template matching; it never executes those
count/sum queries. A template match suggests candidate source code and does not
prove which task called it.

Connection IPs are matched to the inspected Docker project services in memory;
only service candidates and `unique`/`ambiguous`/`unmapped` classification are
printed. Addresses, SQL text, parameters and arbitrary application names are
suppressed. A connection shared through a proxy may remain unmapped. Runtime
inspection and database identity must remain stable across the observation.
There is no cancellation, session termination, container stop, setting change,
cursor advance or normalization. Diagnosis may use the current tooling commit;
any later resume must still use the journal's original creation commit.

The internal observation-only client also allows only read commands and retains
journal/log caps while omitting the old write-consumption check. It rejects
`migrate` before sending a request. Normal clients check the original consumption
budget before sending any command. This distinction does not reset or enlarge
a writer's budget. Use the diagnosis command for old sessions rather than
starting a normal `Client` directly.

## Checkpoints, recovery and retention

Before any write, a full bounded original snapshot is fsynced to a raw slot,
then its target/digest is fsynced as pending in `state.json`. A cursor advances
only after semantic and runtime verification. If the commit response disappears,
resume first inspects the same pending rows. A normalized result is checkpointed
without another update; unchanged originals may retry only within the original
time/resource window. A durable commit measurement survives a lost cursor
checkpoint. A failed transaction or changed rows never advance the cursor.

A finished session stays finished. An expired pending transaction whose rows
are still original may finish as abandoned: its raw slot is retained, its cursor
does not advance, and the next session can revisit the range. An active orphan
client is reported rather than replaced; it expires after at most 60 seconds
idle. `--status --state SESSION_STATE` reads the saved checkpoint and client
presence only; it explicitly does not verify current database rows. `--resume`
performs reconciliation before any further DML.

When an old client stopped before UPDATE and a new session needs the corrected
tooling, close its unchanged pending target using current clean tooling:

```bash
python3 deploy/scripts/v10_normalization_session.py --close-unapplied \
  --state SESSION_STATE
```

This starts a read-only client using the journal's frozen script. It requires
the original runtime/database identity, no active maintenance client and no
saved commit result. It verifies the last committed anchor and proves the
pending row counts, hashes, semantics and migration records still match the
original snapshot. A normalized or changed target is refused; use normal
creation-commit reconciliation for a possible commit. No UPDATE is requested.
Expired write-time/storage-consumption budgets do not prevent this read-only
proof, but it still enforces private journal permissions and size limits.

Successful closure saves the original state as private `close-before.json`,
records its digest and the tooling commit, retains the raw pending snapshot as
`abandoned` and finishes with `unchanged_pending_target_closed`. Counters, WAL
charges, cursor, checkpoint digest, original inputs and interrupted-attempt
timing remain unchanged. Retrying closure is idempotent. A successor can revisit
the same pending range with new tooling; it inherits the maintenance baseline
and consumed phase rows. Closure does not reset the 250,000-row vacuum-review
gate or count an uncommitted target as normalized.

For **new session journals only**, raw snapshots rotate between `raw-0.json`
and `raw-1.json`. Preparing a third transaction replaces the older raw snapshot;
the pending/current transaction and the preceding snapshot remain. Compact row
hashes/targets for the latest checkpoint, cumulative counters, a hash chain tip
and the last 25 receipts remain independently of rotated snapshots. This means
per-row rollback data for older session transactions is deliberately not retained.
The operator's existing manual, unverified recovery policy still applies.

A session directory has a 64 MiB cap, including a 16 MiB private log cap; all
new session directories together have a 256 MiB cap. Another preparation must
reserve 64 MiB of that aggregate allowance first. These guards prevent a long
sequence of finite executions from silently accumulating full-table snapshots.
They can stop before a nominal row cap. No old pilot, sample, batch or finite-run
directory is deleted or compacted: those loaders depend on their frozen files.

Inspect the concrete retention inventory without deleting anything:

```bash
python3 deploy/scripts/v10_normalization_session.py --retention-plan
```

Protect all pending/unfinished sessions and the newest two new session
directories. Older finished new sessions are archival candidates; the inventory
prints their exact paths and sizes. There is no automatic deletion command.
The next session copies its starting proof into its own frozen inputs and loads
only its latest checkpoint/pending snapshot; it does not re-read the full
ancestry. After verifying the successor, an operator can archive older eligible
new sessions according to the chosen manual recovery policy. Keep legacy
journals separately. These are private configuration/row files and must remain
private in any archive.

Continue from a finished new session using:

```bash
python3 deploy/scripts/v10_normalization_session.py --prepare \
  --after-session FINISHED_SESSION_STATE
```
