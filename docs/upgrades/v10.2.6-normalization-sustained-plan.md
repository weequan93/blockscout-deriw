# Sustained normalization: requirements after the bounded pilots

The v10.2.6 application and 29 reviewed schema versions are deployed. The
normalization pilots verified 25,144 stored rows, with no application restart,
historical RPC, global completion record or heavy index/PK work. The latest
verified cursor is below block `132038224`, in private child journal
`batch-20261104T071440Z-46553c32`. The two finite runs remain finished with
their original limits. This document is a design scope; it does not enable a
long-running job or change PostgreSQL settings.

## What the measurements establish

The latest finite run committed 18,347 rows in 19 transactions. Individual
transaction checks took 929–1,462 ms. Successive batch preparations were roughly
20 seconds apart, including release checks, client startup, inspection and
journaling. Those separate costs make the current tool useful for finite pilots;
its end-to-end rate is not a full-table performance forecast.

The measured chunk WAL sum was 122.20 MiB; net filesystem consumption was
177.68 MiB, including unrelated writers and private files. The last two batches
produced more observed WAL than earlier ones. Full-page writes are on and WAL
compression is off, but these measurements do not isolate the reason for that
variation. There are no replication slots and archiving is off in the captured
resource report. `max_wal_size=1024MB` is not a filesystem hard limit.

The catalog estimates 1,776,221,184 rows, with approximately 592 GB of heap and
987 GB of indexes (decimal units). Only 121 of the first 6,797 updates were HOT.
The normal update/delete autovacuum threshold is approximately 355 million dead
tuples at the observed settings; no table-specific override was present. A
sustained update cannot assume that the current vacuum policy will control its
space use. The xmin age in the report is measured in transaction IDs, not time;
it is not proof of a particular long-running session.

## Execution requirements

1. Preserve an immutable source/image/database/heap identity and the current
   hold on all automatic migration workers. Never restart the historical
   duplicate-reindex worker whose completion record already exists.
2. Reuse a bounded SQL client for a finite set of transactions to reduce repeated
   startup overhead. Keep application readiness and identity checks before and
   after writes, with a defined maximum gap between observations. Do not start
   the unbounded global worker or its `max(block_number)` search.
3. Keep indexed, bounded selection and exact row/size limits. Record the pending
   target and reconciliation hashes durably before requesting an update. Advance
   a cursor only after committed semantics and runtime checks are verified.
4. Retain the existing atomic statement/time/WAL checks. Lost responses must
   reconcile without another update, and unknown WAL must consume its allowance.
   A finished run must remain finished rather than reset its budget.
5. Separate run limits from transaction limits. The next implementation pilot
   should initially retain the existing 1,000-row transaction limit, 128 MiB
   measured WAL budget, 512 MiB net space guard and 200 GiB free-space floor.
   A higher transaction size needs its own database validation.

## Vacuum, storage and journals

Measure index/heap growth, dead tuples, vacuum progress, effective table settings,
retained WAL and snapshot age over controlled intervals. Do not infer working
space by multiplying a small pilot's WAL or filesystem observations.

The pilot takes a brief `SHARE ROW EXCLUSIVE` lock to prevent block expansion.
A sustained design must cooperate with vacuum and other writers; repeating a
conflicting lock indefinitely is not an acceptable maintenance strategy. Review
the writer-hold assumptions and exact-row targeting before changing that lock.
Do not run `VACUUM FULL`, rebuild the table or drop indexes as an incidental
part of normalization.

Keep the operator's already accepted manual, unverified recovery policy; do not
introduce another full-database snapshot requirement. Retain all existing pilot
journals. A sustained implementation needs an explicit bounded policy for new
raw snapshots and logs, with durable hashes/checkpoints and reconciliation data
for the pending transaction. Retaining every full row snapshot across the whole
table has not been budgeted. Any new retention behavior must be concrete in its
implementation and run description before use.

The current 512 MiB maintenance memory and default cost controls are observations,
not a reviewed vacuum tuning proposal. Select a vacuum strategy only after
measuring its I/O and its ability to reclaim index/heap space while normalization
runs. Long transactions must be identified using bounded aggregate metadata;
do not terminate sessions automatically.

## Completion boundary

A stored-row cursor does not prove missing historical traces were fetched.
Historical RPC and the trace fetcher remain held. Review null block numbers,
concurrent inserts and the upstream migration's exact completion semantics
before changing its completion record/cache. Unique-index creation, not-null
validation, PK conversion and the two deferred custom index migrations each
retain their separate space and compatibility review.

The application can continue on the verified v10 release while this work remains
held. Deployment/configuration handover can be completed independently of a
full-table data rewrite.
